# 자료 검토와 재검증

## 운영 경로

공개 사이트는 정적 ES modules와 GitHub Pages를 유지한다. 로컬 관리자는
`PYTHONPATH=src python3 -m esports_data.cli admin --reviewer owner-reviewer`로 시작한다.
출력된 loopback 주소를 연다. 토큰은 fragment에서 세션 저장소로 옮기며 서버 로그에 남기지 않는다.
서버를 종료하려면 Ctrl-C를 누른다. Node/npm 의존성과 Python 3.11 이상이 필요하다.

로컬 DB는 `artifacts/workbench/reviews.sqlite3`다. 공개 빌드에 DB, 관리자 화면,
검토 중 자료가 들어가지 않는다. 이 DB를 잃으면 아직 Git으로 전달하지 않은 승인·초안·점검 이력도
잃으므로 서버를 중지한 뒤 DB와 WAL 파일을 함께 비공개 백업한다.

## 승인과 출판

1. 기존 사례 또는 신규 사례 작성을 선택한다.
2. 원문을 직접 열고 공식 기관, 대상 사건, 기간을 확인한다. 링크 점검 버튼은 문서 해시만 가져온다.
3. 판정 이유, 확인일, 공식 근거 URL·요약·해시·기관 ID를 입력한다. 기관 ID는 `config/sources.toml`의 활성 출처 `publisher_id`와 일치해야 하며 URL도 해당 기관 도메인에 속해야 한다. 새 기관은 먼저 출처 정책을 검토해 등록한다. 신규 사례는 지역·분류·유형도 입력한다.
4. 변경안을 저장한 뒤 표시된 JSON을 확인하고 **직접 확인했다는 확인란**을 선택해 승인한다.
5. 출판 미리보기 내보내기를 실행한다. `artifacts/workbench/export/manifest.json`에 파일 해시가 기록된다.
6. 작업 브랜치에서 기존 승인 이력의 prefix가 보존되는지 확인하고 내보낸
   `approved-reviews.v1.json`을 `data/approved-reviews.v1.json`에 반영한다.
   후보 판정도 내보냈다면 두 discovery 장부를 함께 검토한다. 공개 site JSON을 직접 복사하지 않는다.
7. `npm run extract`, 전체 데이터·Python·브라우저·릴리스 검증, NERV 기록, PR 병합을 진행한다.
   정상 Pages 승인 게이트가 통과해야 배포된다. 내보내기는 배포가 아니다.

기존 CLI로 후보를 검토했으면 관리자 서버를 다시 시작해 장부를 재수입한다.
로컬 판정과 Git 판정이 충돌하면 작업을 중지하고 두 판정의 근거를 대조한다.
기존 주간 수집 워크플로의 JSON은 교환 장부로 유지한다. 로컬 초안·승인 명령은 SQLite 트랜잭션으로 처리한다.

## 데이터 계약

- 기준선 230건과 기존 추가 사례는 변경하지 않는다. 승인된 정정과 신규 사례는 별도 append-only 이력으로 적용한다.
- `prior_sha256`은 정정 직전 공개 레코드의 정렬 키 canonical JSON 해시다. 신규 사례는 null이며 기존 ID와 충돌하면 차단한다.
- 승인 이력 ID는 유일하다. 같은 원본과 이력을 다시 투영하면 같은 결과가 나온다.
  이미 적용한 결과에 이력을 다시 적용하거나, 다른 입력 위에 적용하면 충돌로 차단한다.
- 정정 가능 필드는 이름·기관·행정구역·주소·설명·학교급·범위·운영 상태다. 개인 주소 등 PII 검출 내용은 차단한다.
- `current`와 `ended`에는 공식 근거와 운영 상태를 직접 뒷받침한다는 사람 확인이 필요하다.
  `needs_review`는 최근 검토 시도를 기록하되 `status_checked_at`을 검증일처럼 채우지 않는다.
- 근거의 SHA-256·기관 ID와 공개 source ID를 함께 보존한다. 기존 마이그레이션/원문 crosswalk는 기준선 계보이고,
  승인 이력의 해시와 추가 source는 이후 정정·신규 사례의 계보다.
- `meta.data_updated_at`은 실제 승인 변경 반영일을 포함한다. 변경 이력이 없으면 기존 날짜를 유지한다.
  `meta.last_reviewed_at`은 최근 검토일이다. 배포일과 다르다.
- 운영 재검토는 기본 90일, 종료 사례 근거 점검은 365일이다. 공개 화면은 날짜가 지나면
  재검토 필요로 표시하지만 과거 승인 상태와 근거를 삭제하지 않는다.

기존 subject/claim 불변 스냅샷 출판 CLI는 별도 보호 경로를 유지한다. 이 작업의 사이트 투영 이력은
그 스냅샷의 출판 영수증이 아니다. 사이트용 내보내기를 `publish` 승인으로 간주하지 않는다.

## 수집과 시범 운영

`PYTHONPATH=src python3 -m esports_data.recheck --batch pilot`로 우선순위 30건,
`--batch all`로 전체를 점검한다. 기관·학교 사례, 확인일 없음, 오래된 연도, ID 순으로 선정한다.
사례당 최대 3개 등록 URL을 4개 worker로 점검한다. 원문은 일시 처리하고 결과 코드와 해시만 저장한다.
이 명령은 사실 판정을 하거나 공개 상태를 변경하지 않는다. 점검 결과에 따라 미승인 초안을 만들며, 이미 저장한 초안을 덮어쓰지 않는다. 관리자에서 사례를 선택한 뒤 변경안 수정을 눌러 근거를 보완한다.

후보의 `event_sha256`은 제목에 연도·지역·기관·행사 정보가 모두 있을 때만 생성하는 중복 제안이다.
다른 연도는 같은 사건으로 묶지 않는다. 관리자에서 연결된 공식 근거 찾기를 누르면
기사에 연결된 등록 기관 URL을 최대 5개 확인한다. 직접 연결이 없으면 수동 확인 대상으로 남긴다.
등록된 공식 홈페이지도 자료의 사실성이나 현재 운영을 자동으로 증명하지 않는다.

실제 점검 집계는 `reports/review-rollout.v1.json`에 기록한다. 개별 결과는 로컬 DB에만 남긴다.
공식 출처 확보율·중복률은 각각 승인 이력과 URL 후보 수를 분모로 하며, 사건 수나 신규 공개 건수로 바꾸어 해석하지 않는다.

## 검증·복구

- `PYTHONPATH=src python3 -m unittest tests.python.test_workbench`
- `npx playwright test --config playwright.admin.config.mjs`
- `npm run verify:release`

출판 전 오류는 내보낸 제안 파일을 반영하지 않고 수정한다. 공개 이후 정정은 새 승인 이력을 추가한다.
배포 회귀는 `docs/pages-release.md`의 이전 승인 commit 재배포 경로를 따른다.
개인정보 사고는 기존 제거 전용 긴급 철회 경로를 사용한다. 이 관리자는 승인 게이트를 우회하지 않는다.
